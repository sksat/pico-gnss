# Pico 間リンクの時刻同期

Pico 2 台を GPIO で直結し、10BASE-T のロジックだけでフレームをやりとりして、その上で時刻を同期させた回の図。

結論と数値は PR に書いてあるので、ここはその図と、図を作るスクリプトを置く場所である。
生データは repo top の `logs/20260820-pico-link/` にあり、gitignore 配下なのでコミットしない。

2 台は **Pico server** (GNSS 受信機が繋がっていて NTP を配る側) と
**Pico client** (GNSS を持たず、届いた NTP だけで時刻を作る側) と呼ぶ。

## 配線

![Pico 2 枚を直結し、両方の 1PPS をオシロで見る](fig-link.svg)

GNSS 受信機は Pico server にしか繋がっていない。
Pico client が知っている時刻は、この 4 本の線を渡ってきた NTP パケットから作ったものだけである。

各方向 2 本なのは、送信側が 2 ピンを対で駆動していて、線の上の状態が 3 つあるためである
(`0b00` idle、`0b01`、`0b10`)。
片側だけ見ると idle と `0b01` が区別できず、フレームの終わりが決められない。

### どうやって合っているかを測るか

Pico server と Pico client の両方が、自分が思う秒のはじまりに GP6 を立ち上げる。
GNSS 受信機も自分の秒のはじまりに 1PPS を出す。
この 3 本を同じトリガでオシロに取れば、受信機を基準にした差が、そのまま「その板の時刻がどれだけずれているか」になる。

**2 本の 1PPS は、形は同じでも由来が違う。**
Pico server のものは GNSS 受信機の 1PPS で規律した時刻、つまり GPSDO の出力である。
Pico client のものは GNSS を持たず、リンク越しに届く NTP だけで規律した時刻である。
この違いが、そのまま 2 本の散らばりの違いになって出る。

受信機の 1PPS は active low なので、秒を指しているのは**立ち下がり**である。
以下の図はどれも、その立ち下がりを 0 とした軸で描いてある。

## 図

### `fig-scope-annotated.png`

1 回の取り込みを、どの線が何なのかを書き入れて描き直したもの。
オシロの画面そのものは `fig-scope-5us.png` にある。
こちらは画面ではなくその裏のサンプルから描いてあるので、軸と注記を自分で付けられる。

横軸は秒境界からの時間で、単位は µs。
上から CH1 が GNSS 受信機の 1PPS、CH3 が Pico server の GP6、CH4 が Pico client の GP6 である。
受信機の 1PPS は active low なので立ち下がりが秒を指し、それがトリガでもあるので軸の 0 になる。
矢印は 0 から各 GP6 の立ち上がりまでの距離で、これがその板の時刻のずれである。

**1 回の取り込みは分布から引いた 1 点であって、オフセットではない。**
この取り込みの Pico server は −0.81 µs だが、同じ 140 回の平均は +0.29 µs (sd 1.24) である。
Pico client も −3.12 µs に対して平均 −5.22 µs (sd 2.97) で、どちらも 1 枚では 1σ ぶん外れうる。
表題にこの両方を書いてあるのはそのためで、判断は次の 2 つの図の分布で行う。

### `fig-scope.gif`

同じ描き方で連続した取り込みを並べたもの。
下段は各回の値をそのまま並べた時系列である。

140 回ぶんで、1 枚では止まって見える 2 本の 1PPS が秒ごとに動いていることが見える。
オシロは 1 回の取り込みと読み出しに数秒かかるので、毎秒ではなく数秒おきの間隔である。

### `fig-broadcast-series.png`

同じ差を 90 回、約 8 分にわたって取ったもの。
このときの Pico client は broadcast だけで同期している。

横軸は取り込みの回数で、5 秒に 1 回ほどの間隔である。
縦軸は受信機の秒からのずれで、単位は µs。
**0 の線が受信機の秒**で、上が遅れ、下が進みになる。
右の柱は同じ値のヒストグラムである。

青の Pico server は 0 のまわりに 1.4 µs で散っている。
橙の Pico client は ±8 µs のあいだをゆっくり往復していて、これは白色雑音ではない。
測定のばらつきではなく、時刻を追い込むループが 3 分ほどの周期で行き過ぎては戻っている応答である。

### `fig-ntp-accuracy.png`

同期の精度をどう言えばよいかの図。

受信機を基準にした絶対位置には、Pico server 側の較正定数がそのまま乗る。
その定数は firmware が UTC の錨をどこで取るかで決まり、ビルドによって数十 µs 動く (次節)。
一方 **Pico client GP6 − Pico server GP6** は、同じ 1 回の取り込みから両方を読んだ差である。
Pico server の定数はその板の時刻そのものを動かし、GP6 にも送るパケットにも等しく乗るので、この差からは落ちる。
残るのは、NTP がどれだけ忠実に秒を渡せたかだけである。

左は run ごとの分布で、点が各取り込み、丸と横棒が平均と標準偏差、灰色の帯が ±10 µs。
右は同じ差を、その run の Pico server の絶対位置に対して並べたものである。
Pico server が受信機から 0 µs のときも +204 µs のときも、差は同じ帯に収まっている。

**NTP としての同期精度は、run ごとの平均で −8.1 〜 +9.7 µs、run 内の揺れは sd 0.6 〜 3.5 µs である。**
Pico server 自身が GPS からどれだけずれているかとは、別の量になる。

### `fig-scope-5us.png`

オシロの画面そのもの。黄が CH1、紫が CH3、青が CH4 にあたる。

## UTC の錨を取る場所

`fig-ntp-accuracy.png` の右で Pico server の絶対位置が 0 µs から +204 µs まで散っているのは、
そう振らせたのではなく、そう動いてしまうからである。

firmware は 1PPS を PIO で捕まえて ns のタイムスタンプを作る。
しかしそれを UTC に結びつける錨は、PIO が捉えたエッジそのものではなく、
**FIFO からその値を汲み出したときにソフトウェアの時計を読んだ値**である
(`rp_pps::embassy::run_capture` が `on_pps_edge(edge, query_ns())` と呼ぶところ)。
executor がそのタスクを起こすのが遅れれば、遅れた分だけ UTC が手前にずれ、出力もパケットも同じだけ遅れる。

確かめるために、汲み出しの直前に既知の 100 µs の待ちを入れた。
予測は「出力が同じだけ遅れる」で、実測は +80 µs から **+204.1 µs** (sd 1.4、n=16) だった。
同じ取り込みで Pico client も +197.4 µs へ動いていて、パケット越しにそのまま付いてきている。

`CLOCK_OFFSET_NS` はこの遅れを埋めるために置いた定数である。
遅れは秒境界で executor が何を先に動かすかで決まるので、同じビルドなら再現する
(5 回起動し直して +79.7、+80.0、+80.3、+80.7、+82.3 µs) が、firmware が変われば合わなくなる。
**この定数に寄りかかっているあいだは、受信機に対する絶対の精度は主張できない。**
錨を PIO の tick の側で取れば消える種類の誤差で、それが次の PR の動機になっている。

## スクリプト

`logs/plot_link.py` が `logs/20260820-pico-link/` の CSV を読んで図を書く。

```sh
uv run docs/report/pico-link-ntp/logs/plot_link.py
```

図中に日本語を出すので Noto Sans CJK JP を明示している。
無い環境では豆腐になる。

波形そのものは `scope_pair.py trace` で取る。
画面のスクリーンショットと違い、3 本のサンプルが 1 取り込みぶんずつ残るので、
`fig-scope-annotated.png` と `fig-scope.gif` はそこから描いている。
