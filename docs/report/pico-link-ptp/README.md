# フレームの時刻を PIO で記録する

Pico 間のリンクで、出入りするフレームの先頭ビットの時刻を、ソフトウェアではなく PIO の state machine に記録させた回の図。

結論と数値は PR に書いてあるので、ここはその図と、図を作るスクリプトを置く場所である。
生データは repo top の `logs/20260820-pico-link/` にあり、gitignore 配下なのでコミットしない。

## 何を測っているか

Pico client は「自分の質問の先頭ビットが線に出てから、応答の先頭ビットが着くまで」を測る。
Pico server は「質問の先頭ビットが着いてから、応答の先頭ビットが線に出るまで」を測る。
どちらも自分の state machine が自分のピンを見て記録する。

2 つの差が経路である。
この配線はジャンパ 2 本なので、経路は ns しかないはずである。

## 図

### `fig-path.png`

横軸は、Pico client が測った往復時間から Pico server が測った折り返し時間を引いた値である。
残るのは信号が線の上を渡るのにかかった時間で、この配線はジャンパ 2 本なので、本来は 0 に近いはずである。
単位は µs。
縦軸はその値が何回出たかで、赤い縦線が中央値である。

どちらの板も測っているのは自分の中での**長さ**なので、板どうしの時計が合っているかどうかは関係しない。
時計のずれが結果に入らないのが、この測り方の要点である。

左が、カウンタが何回止まったかを呼び出し側で数えていたとき。
カウンタはピンを跨ぐものすべてで止まるのに、数えていたのは関心のあるフレームだけだったので、補正が毎秒ずれていった。
散らばりは実際のばらつきではなく、その数え損ねが増えていく様子である。

右が、カウンタ自身に数えさせたあと。
中央値が動いただけでなく、散らばりが 895 ns から 12 ns に潰れ、対応づけも全数一致した。

残る 592 ns の出どころは分かっていない。
両端とも同じ物理エッジを 16 ns 分解能で見ているので、原理的には 0 に近いはずである。

図では、順番の対応づけに失敗した回を中央絶対偏差で切り出して除いてある。
除いた数は図に出してある。

## 4 本を 1 回の書き込みで起動したときの 1PPS

#10 が 1PPS の錨をカウンタの側へ移したので、この PR の監視 2 本も同じ書き込みに入る。
PIO0 の 4 本 (1PPS の捕捉、1PPS の出力、リンクの入口、リンクの出口) が同時に走り出し、
その瞬間が 4 つのカウンタに共通のゼロになる。

受信機の秒に対する Pico server の GP6 は **−2996.2 ns、sd 6.2 ns (n=16、幅 26 ns)**。
起動直後から締まっていて、移行もない。
捕捉が #10 とは別のプログラム (`event_capture_program`) を走らせるので固定の位置は違うが、
どちらも動かない。

Pico client はこの run で +58.4 µs 離れている。
送信の定数 (`TX_LAG_NS`) がまだ古い較正のままで、正しくなった時計と噛み合っていないためである。
この PR のタイムスタンプは、その定数を測り直すための計器にあたる。
